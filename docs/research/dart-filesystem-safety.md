# Dart filesystem safety: links, replacement, removal and ledger updates

Research for [issue #12](https://github.com/louiss0/agent_resource/issues/12), informing (not deciding) [safety issue #6](https://github.com/louiss0/agent_resource/issues/6).

## Context, method and evidence boundaries

- **Retrieved 2026-10-23 UTC.** Read #12, #6 body and comments (the API returned zero comments on #6 at retrieval), and the [authoritative destination amendment](https://github.com/louiss0/agent_resource/issues/5#issuecomment-6354750934). ## Executive result

Portable `dart:io` can support ordinary link-aware operations and recoverable multi-step designs under the **chosen bounded trusted-local-root, non-hostile-writer assumptions**; it is **not a security boundary or a multi-object transactional filesystem**. Specifically:

| Required guarantee | What the evidence supports |
| --- | --- |
| Link creation and unlink without intentionally deleting its target | Documented `Link.create` and nonrecursive `Link.delete`; true Windows symlinks in this SDK, not junction creation. Stable/trusted parent paths are still required. [D1] [D4] [SW] |
| Detect a final symlink, including a broken one | `type(path, followLinks: false)` / `Link.exists`; not full `lstat`, not protection against linked ancestors or subsequent substitution. Lookup errors can collapse to `notFound`. [D3] |
| Protect unmanaged collisions against racing writers | No portable no-clobber rename; check-then-rename is insufficient. Need cooperative exclusion/trusted namespace or native OS-specific primitives. [D1] [D2] [D4] [SL] [SM] [SW] |
| Atomically replace a nonempty installation directory, preserving old tree as backup | Not available as one `dart:io` operation. Ordinary directory rename cannot replace a nonempty destination. Two renames leave intermediate states; native exchange facilities vary. [D2] [PLR] |
| Remove only the baseline-unchanged object in the presence of hostile changes | SDK hashes/checks cannot atomically bind verification to deletion, nor snapshot a mutable tree. Stronger native namespace control and a writer/snapshot assumption are needed; no generic absolute guarantee established. [D3] [SL] [SDL] [PO] [PU] |
| Atomically commit installation plus per-scope JSON ledger | No multi-path transaction API. Even atomic single-name rename is not a joint commit. Journal/recovery and ordering are necessary for a recoverability claim; stronger crash guarantees need native durability work and a defined storage contract. [PR] [PLF] [SF] [SW] |
| Preserve permissions/metadata identically everywhere | No portable metadata-preserving tree-copy contract; implementations differ materially. `FileStat.mode` is not a portable ACL or complete identity/baseline API. [D1] [D3] [SL] [SM] [SW] [AC] |

“SDK-only” here means **portable `dart:io`**, not that Dart cannot call native APIs. `dart:ffi` bindings could use OS primitives without choosing a third-party package; that is an OS-specific implementation with additional verification obligations, not a portable `dart:io` guarantee. No package or product architecture is selected here.

## Narrowed-case feasibility (current user policy)

| Case | Portable SDK feasibility and precise limit |
| --- | --- |
| Validate a copied resource; refuse root/internal links | `type(..., followLinks: false)` and non-following listing can find stable final links; all relevant root/ancestor components and internal entries need examination. There is no atomic read-beneath/no-follow API. A linked ancestor or an entry substituted after checking can escape the disclosed root. SDK-only confinement therefore requires trusted stable namespace/content assumptions; strong adversarial confinement needs native traversal controls. [D2] [D3] [SL] [SM] [SW] [PO2] |
| Validate a top-level linked installation | The **one permitted traversal** is from the installation link into its disclosed content root; internal links are not thereby allowed. Resolve/disclose/check that root for validation, then apply the same no-internal-link/budget restrictions. No link-tree policy is needed. The top-level target need not be readable/resolvable merely to unlink an otherwise verifiable owned link. [D3] [D4]; policy supplied by user. |
| Verify link ownership without target content | `type(false)` + `Link.target` can inspect the link even when the referent is broken; do **not** use target `stat`, target manifest or resolved-target existence as an unlink gate. However, portable `FileStat` supplies no persistent link-object ID, `identical` compares only two current paths, and `type(false)` does not distinguish Windows link/reparse subtypes. A strict stored OS-identity/type fingerprint cannot be implemented by these APIs alone. Windows `Link.target` returns a decoded substitute name with a leading `\\??\\` removed, not a complete raw reparse record. A recreated same-text link cannot be distinguished from the old link using only stored type+target text. [D3] [D4] [SW] (`LinkTarget`, `AreIdentical`) |
| Unlink a verified link, including broken/drifted target | Nonrecursive `Link.delete` is the correct SDK operation under stable-parent/entry assumptions: POSIX unlink or Windows reparse-aware RemoveDirectory/DeleteFile. No recursive target delete is needed or authorized. Type/target verification and deletion are still separate syscalls; Windows attribute check then delete is also separate. Final-link unlink semantics do **not** provide identity-conditional unlink or secure ancestor traversal. [D4] [SL] [SM] [SW] [PU] [WD] [WDR] |
| Replace a managed link with retained backup | Back up the **entry**, not target contents. `Link.rename` to an unused same-parent name does not need a readable target; relative target semantics must be preserved. Backing up then publishing is multiple operations, has a visibility gap, and is not racing-writer no-clobber. Never interpret Windows direct link-over-link rename as universally atomic: SDK can pre-delete a destination directory link. [D4] [SW] [WM] |
| Remove/replace a copied installation | Verify whole unchanged manifest, not just main document or managed-ledger status. Source staging plus retained old tree permits recovery under the stated writer assumptions, but no SDK atomic full-tree compare-delete, no atomic nonempty-tree replacement, and no joint ledger commit exist. Edited/unverifiable/unmanaged old content fails the chosen gate; native rename alone does not prove content unchanged. [D1] [D2] [D3] [PR] |
| Dry-run | A read-only planning path can avoid explicit filesystem writes: no temp/staging creation, write-open/truncation, ledger rewrite, backup/recovery/cleanup or lockfile creation. In particular an exclusive Dart file lock requires a write-open; do not create/open-for-write a lock merely to preview. It cannot promise later mutation succeeds or inventory remains current. Ordinary read IO can trigger OS-managed access-time changes or filter activity; “no app-initiated writes” is not “no physical storage change anywhere.” [D1] [D2] [D3] [WR] |

**Hard limitation to carry into safety #6:** if “link's own identity” means a persisted native file ID and exact Windows directory-symlink/junction type, native metadata access is needed. If it means location plus observable SDK link type/decoded target under cooperative stable-namespace assumptions, that is a weaker identity definition which must be explicit—not silently substituted for the stronger one. Neither definition alone closes hostile check-to-unlink races. The target's content drift is **not** part of the link-entry ownership/removal gate under the user's decision.

The broader primitive details below explain these limits; internal linked trees and linked roots are **rejection cases**, not proposed supported features.

## 1. Links, junctions, reparse points and hard links

### 1.1 Creating and recognizing links

- **D/S:** `Link.create` uses POSIX `symlink`/`symlinkat` on macOS/Linux. Relative targets are interpreted relative to the directory containing the link. The target need not exist. An existing link path is an error. Recursive creation may create **parents of the link path**, not a target tree. [D4] [SL] [SM]
- **D/S:** In **3.13.2 Windows, `Link.create` creates a true symbolic link, explicitly not a junction**. It selects directory-link versus file-link from the existing target's type; a missing target produces a **file-link**. The type does not adapt if a directory later appears there; resolving a mismatched type can fail. Administrator privileges or Developer Mode are required according to the SDK contract. Source invokes `CreateSymbolicLinkW`, with `SYMBOLIC_LINK_FLAG_ALLOW_UNPRIVILEGED_CREATE` and the directory flag when appropriate. There is no public link-kind parameter or documented automatic junction fallback. Do not use older SDK junction behavior as the current contract. [D4] [SW] (`CreateLink`, lines 645–737)
- **D:** Windows junctions are directory reparse points; they can reference directories on different **local** volumes. Hard links are different: multiple directory entries for one file on the same volume, not directory links. [WH]
- **S:** Windows `GetTypeAndAttributes(..., false)` classifies reparse points as `link`, except the AF_UNIX tag classified as a socket. This is **broader than “a supported symlink or junction.”** `Link.target`'s native reader recognizes `IO_REPARSE_TAG_MOUNT_POINT` and `IO_REPARSE_TAG_SYMLINK`, and errors on other tags. Dart does not expose a general reparse-tag inventory in this API. [SW] (`GetTypeAndAttributes`, `LinkTarget`)
- **D/I:** Reparse points can be custom/filter-backed data or mounted folders, not merely symlinks. A path classified `link` is therefore insufficient evidence of permitted link semantics, absence of remote hydration, or safe/offline traversal. Unknown tags must not silently become ordinary directory links under an “offline/local” claim. Whether to refuse them or add a native tag-aware implementation is unresolved. [WR] [SW]

### 1.2 Hard links are aliases, not isolated copies

- **D:** POSIX `link` creates another name for the same existing file; cross-filesystem linkage can fail with `EXDEV`. Windows documents same-volume file hard links and immediate visibility of writes through other hard links. Removing one directory entry is not the same as erasing all aliases. [PH] [PU] [WH]
- **D/S:** The examined public `File`/`Directory`/`Link` APIs have **no hard-link creation API**. `Link.create` is not one. `FileSystemEntity.identical` can detect that two known existing hard-link paths name the same object, but `FileStat` exposes neither inode/device identity nor hard-link count; there is no SDK alias-enumeration guarantee. [D1] [D2] [D3] [D4] [SL] [SM] [SW]
- **I:** A hard-linked backup is not a content snapshot: an in-place edit through another name changes it too. Independent destination files in a fresh, unoccupied staging tree avoid intentionally sharing source inodes, but copying a mutable source still does not produce a coherent point-in-time snapshot; moving a copied installation into backup also retains any pre-existing external hard-link aliases. `identical` can check known pairs, not establish that no unknown aliases exist. In-place writes to a destination or ledger with hard-link aliases can change an otherwise unrelated name. Canonical path comparison alone does not discover these aliases. Hashing an entry does not demonstrate exclusive ownership of its underlying file. [PH] [WH] [D3]

## 2. Metadata, following behavior and safe unlink

| Operation | Documented or observed behavior | Safety limit |
| --- | --- | --- |
| `FileStat.stat`, entity `.stat` | Follows a final symbolic link and returns target metadata. Public fields: times, type, mode, size. [D3] | Not an `lstat` of link metadata; no inode, device, link count, ACL, reparse tag or durable handle. Windows `changed` is creation time, not POSIX ctime. |
| `type(..., followLinks: false)` | Reports final link rather than target. Linux uses `fstatat(..., AT_SYMLINK_NOFOLLOW)`; macOS uses `lstat`; Windows uses attributes/tag logic. [D3] [SL] [SM] [SW] | Ancestor links still resolve. Documentation says `notFound` on **any lookup error**, not only absence; it is not positive proof a name is free. |
| `Link.exists`, `File.exists`, `Directory.exists` | Link existence is link-aware; File/Directory existence is type-specific and generally follows links. [D3] [D4] | A `false` result cannot certify absence of other entry types; broken links matter. |
| `Directory.list(followLinks: false)` | Reports links as links, does not recurse into them; default is `true`. Recursive following has cycle handling for the same descent. [D2] | Listing is not a frozen snapshot or a global budget. Cycle handling does not prevent huge finite expansions or duplicated traversal through aliases. |
| `File` reads/writes/open | Class documentation says methods generally act on the ultimate target, except delete. [D1] | A prior link-aware check does not make later open no-follow. Source allows pipes/character devices in some open paths; “can open” is not evidence of a regular inert file. [SL] [SM] |
| `File.copy` | Overwrites an existing file, no transactional/tree snapshot contract. Linux opens destination with `O_TRUNC` and follows source/final destination links. macOS uses `copyfile(..., COPYFILE_ALL)`. Windows source rejects a source entry classified as a link and uses temp-copy/move or direct-copy fallback. [D1] [SL] [SM] [SW] | **Documentation/source qualification:** the broad File-class link statement does not establish identical native copy behavior; Windows pinned source is narrower. Do not blindly use copy as a no-follow, no-clobber or portable link-materialization primitive. |
| `Link.delete(recursive: false)` | Deletes the link, errors for a nonlink. POSIX uses unlink; Windows chooses `RemoveDirectoryW` for directory reparse points and `DeleteFileW` otherwise. [D4] [SL] [SM] [SW] | Correct operation for unlinking a stable managed link entry; not an atomic identity-conditional delete. |
| `Directory.delete` / recursive delete | Documentation: final directory link deletion removes link, not target; recursive deletion does not follow links. `recursive: true` can delete an object **regardless of type**. [D1] [D2] [D4] | Not unchanged-only, not rollbackable, may partially remove a tree on failure, and **not a defense against concurrent namespace substitution**. See §4. |

**D:** POSIX unlink of a final symlink removes the link, not its named target. Windows `DeleteFileW` documents the same; `RemoveDirectoryW` explicitly removes a junction without affecting the target even if the target is nonempty. These are final-entry semantics, not a promise that every ancestor was traversed without following a link. [PU] [WD] [WDR]

**I:** Keeping the link entry and its resolved target as distinct authorities is essential. Renaming/unlinking an adopted or installed link must not authorize recursive deletion of its target. A content baseline of the target does not grant ownership of that target, and under current policy target-content drift is not a reason to refuse unlink of an otherwise verified owned link. An existing link inside a copied tree is a rejection case under the narrowed policy, not permission for implicit File API following. The same applies to linked native/configured roots. [D1] [D4] [PU]

## 3. Canonicalization, identity, containment and aliases

- **D/S:** `resolveSymbolicLinks` requires an existing object; native default-namespace Linux/macOS implementations use `realpath`, Windows uses a handle and `GetFinalPathNameByHandle`. Windows resolves `..` before links; other platforms resolve link targets during traversal. A Windows file/directory link-type mismatch can fail. `.absolute` merely makes a path absolute; it does not resolve links. [D3] [SL] [SM] [SW]
- **D/S:** `FileSystemEntity.identical(a,b)` compares the **entries**, not final symlink targets: a link versus its target, or distinct symlinks to one target, are false; linked directory ancestors are followed. Linux/macOS compare device+inode using non-following final metadata. Windows compares volume serial plus high/low file-index fields from `GetFileInformationByHandle`, using `FILE_FLAG_OPEN_REPARSE_POINT`. Handles/stat results are not retained as a mutation capability. [D3] [SL] (`AreIdentical`) [SM] (`AreIdentical`) [SW] (`AreIdentical`)
- **I/U:** These calls are observations, not reservations. Resolved strings do not become durable object IDs, resolve nonexistent future children, enumerate hard-link aliases, or prevent later path replacement. A single string-prefix test is not component-aware containment. Lowercasing paths is not a documented cross-filesystem identity algorithm. No evidence here establishes universal canonical naming across case-sensitive/case-insensitive volumes, Unicode variants, Windows namespace/short-name aliases, bind mounts, or all remote filesystems. Native identity implementations also need filesystem-specific qualification. [D3] [SL] [SM] [SW]
- **D/I:** POSIX inode identifiers may be reused after the last reference is gone. Do not use a previously observed ID or timestamp as permanent ownership proof. `FileStat` is explicitly a snapshot; even metadata equality plus a digest is not a lock against the next change. [PU] [D3]
- **I:** Direct-child eligibility is a logical path/layout check **plus** physical alias/ancestor checks, not a substitute for them. Source=destination, source containing destination/staging, destination containing source, and two configured roots resolving to one physical location can defeat naïve recursion, uniqueness and ledger ownership. Different destination/scope labels cannot make the same physical Shared object independently removable. Ambiguity required for a mutation remains an inability to prove safety, not a license to guess. [D2] [D3]; destination semantics: [amendment](https://github.com/louiss0/agent_resource/issues/5#issuecomment-6354750934).

## 4. TOCTOU and the actual trust boundary

**D/S:** Portable APIs take path strings. There is no public `dart:io` directory-handle-relative open/rename/unlink family, no `O_NOFOLLOW`/`openat2` resolution flags, no Windows reparse-tag selection or general delete-by-verified-handle facility, no “remove this name only if it still has identity X,” and no tree snapshot API in the examined interfaces. Linux native source's use of `*at` and internal namespaces does **not** expose those controls to application code. [D1] [D2] [D3] [D4] [SL] [SDL] [SW]

**Concrete source-supported race, not a local exploit test (S/I):** pinned Linux recursive deletion checks `fstatat(..., AT_SYMLINK_NOFOLLOW)`, then opens a directory with `openat(..., O_DIRECTORY)` **without `O_NOFOLLOW`**. Between these steps a writable entry can become a symlink to another directory. A preliminary “no links” scan and the recursive-delete documentation therefore do not establish adversarial race resistance. Windows recursive deletion similarly checks path attributes then continues using names. This is a security limitation, not an assertion that ordinary stable-link deletion follows targets. [SDL] (`DeleteRecursively`, lines 265–287) [SDW] (`RecursiveDeleter`)

**I:** The same gap exists for `validate → copy`, `hash → delete`, `canonicalize → open`, `inventory → publish` and `check empty → rename`. Rechecking before/after improves detection, but does not remove the final gap. Reading an open regular file can still observe concurrent in-place edits; a directory tree cannot be made an instantaneous snapshot just by hashing twice. Time/byte/entry/depth/link budgets bound workload only when every operation stays within the chosen safe IO model; opening a substituted FIFO can block before a byte budget is consumed. [D1] [D2] [D3] [SL] [SM]

The narrowed no-linked-internals policy reduces supported cases, but it **does not remove these races**: validation must reject an internal link without inadvertently following it before rejection.

**Native primitives that could support a stronger design (not a complete proof):**

- POSIX `openat`/`fstatat`/`unlinkat`/`renameat`, trusted directory descriptors, component-by-component traversal, `O_NOFOLLOW` and `O_EXCL`. `O_NOFOLLOW` applies to the final component; it alone does not secure an arbitrary multi-component pathname. Linux `openat2` adds `RESOLVE_BENEATH`, `RESOLVE_IN_ROOT`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_NO_XDEV` controls, subject to kernel/support/error handling. [PO] [PU] [PR] [PO2]
- Linux `renameat2` no-replace/exchange flags for appropriately supported filesystems (see §5). [PLR]
- Windows `CreateFileW` with reparse-aware and sharing/access controls, tag/identity inspection and a separately designed handle-based mutation layer. `FILE_FLAG_OPEN_REPARSE_POINT` changes handling of the opened entry; this note does **not** prove that adding it secures every ancestor in an arbitrary path or prevents all namespace races. [WC] [SW]

**Boundary:** A native layer can address traversal, no-clobber and retained identity, but **does not alone prevent another authorized writer editing the same file contents** or swapping a final name before a name-based unlink. Strict “unchanged at the instant of deletion” needs a protected namespace plus writer exclusion/snapshot semantics (or a narrower explicitly stated observation-based contract). POSIX advisory locks cannot force arbitrary editors to cooperate. An attacker with the same user's authority may also change manager-owned directories or ledger files. No absolute hostile-same-user guarantee is established here. [PO] [PU] [D1] (locking)

**Chosen SDK-only trust envelope (user decision; feasibility is I):** bounded trusted local roots, no hostile concurrent-writer guarantee; cooperating manager processes and in-process serialization; untrusted resource/ledger data, bounded regular-file/link traversal, observed-drift detection, and failures surfaced with retained recovery evidence. Parent/entry stability during each verified operation remains an assumption, not an SDK-enforced boundary. Within that envelope, link-aware inventory, canonical/identity cross-checks, staging, verification and recovery bookkeeping can be meaningful. If that envelope is unacceptable, OS-specific primitives **and** a sharper writer/storage threat model are required; more path checks are not equivalent.

## 5. Rename, replacement, no-clobber and backup

### 5.1 Single-name operations are not interchangeable

| Interface/platform | Evidence | Consequence |
| --- | --- | --- |
| Dart `File.rename`, `Link.rename` | Existing destination file/link may be removed; existing directory fails. No no-replace/exchange parameter. `Link.update` is explicitly delete then create. [D1] [D4] | No “fail if occupied” publishing contract. `exists` beforehand does not add one. Link update is not atomic. |
| Dart `Directory.rename` | Nonempty existing destination directory fails everywhere; existing empty directory behavior is platform-specific, replaced on POSIX. Existing file/link documented to fail. [D2] | A complete populated installation cannot just be renamed over an existing populated installation. |
| Linux/macOS SDK source | Calls `renameat`/`rename` for these renames. POSIX describes old-or-new visibility at an existing destination and final-link replacement rather than target overwrite. [SL] [SM] [SDL] [SDM] [PR] | A successful supported same-filesystem POSIX rename can provide atomic **namespace visibility for that one rename**, not joint ledger/resource commit or power-loss durability. |
| Windows SDK source | File/link rename uses `MoveFileExW(WRITE_THROUGH \| REPLACE_EXISTING)`; when destination is a directory link it **deletes that link first**, then moves. Directory rename uses `WRITE_THROUGH` without `REPLACE_EXISTING`. [SW] (`RenameHelper`, lines 781–815) [SDW] (`Rename`) | Direct counterexample to a universal atomic link-replacement claim: deletion can succeed then move fail, leaving a gap. Win32 documentation does not establish universal crash-atomic rename across all backing stores. |
| Cross-filesystem/volume | POSIX rename may fail `EXDEV`. Win32 file move to another volume needs `COPY_ALLOWED`, which SDK rename flags do not request; directory moves must be same drive. [PR] [WM] [SW] [SDW] | Stage/backup on the actual destination filesystem. A copy+delete fallback is **not atomic rename**, can leave duplicates/partials, and must not silently inherit rename guarantees. |
| Native Linux `renameat2` | `RENAME_NOREPLACE` rejects an existing destination, filesystem support required. `RENAME_EXCHANGE` atomically exchanges two existing paths, including different types/nonempty directories. Not exposed by `dart:io`. [PLR] | Potential stronger Linux building blocks, not a cross-platform promise or ledger transaction. |
| Native Windows `ReplaceFileW` | File replacement can retain a backup and merge metadata, same-volume requirement. `REPLACEFILE_WRITE_THROUGH` is **unsupported**; documented error cases can leave different intermediate names/attributes. Not Dart rename; no directory-tree replacement contract. [WREP] | “Use native ReplaceFile” is not, by itself, proof of durable all-or-nothing resource+ledger replacement. |

POSIX atomic replacement does not mean both old and new names change simultaneously for all observers, guarantee that open readers see new contents, or promise restoration after a crash. Existing open POSIX file references continue to refer to the old object after replacement/unlink. [PR] [PU] [PLR]

### 5.2 Staging and backup requirements implied by the chosen feature

These are constraints on an eventual design, not a selected CLI, retention policy or implementation recipe.

1. **Prepare new content away from the live installation.** In-place copy/truncate cannot preserve a verified old installation on failure. Validate/hash the actual prepared candidate under existing budgets before publishing; do not treat a mutable source's earlier validation as verification of later copied bytes. Still requires the source/writer assumptions in §4. [D1] [SL] [SW]
2. **Use a trusted, bounded staging/backup namespace on the destination filesystem.** A system temp directory may be a different volume and may be environment-selected. A shared textual parent does not prove same filesystem if mount/reparse boundaries intervene. Random names provide collision avoidance, not durable reservation or permission guarantees. [D2] [PR] [WM] [SDL] [SDW]
3. **Do not assume `Directory.createTemp` is private on every OS.** SDK Linux source uses `mkdirat(..., 0777)` subject to process umask; macOS source calls `mkdtemp`; Windows calls `CreateDirectoryW(..., nullptr)` using default security. The portable API documents uniqueness, not uniform `0700` or explicit ACLs. `File.create(exclusive: true)` offers exclusive creation but returns a path-based File after closing the native descriptor; a subsequent write/open is another lookup. Native permission/ACL creation controls or a verified trusted parent assumption are needed for stronger isolation. [D1] [D2] [SDL] (`CreateTemp`, lines 463–491) [SDM] (`CreateTemp`) [SDW] (`CreateTemp`) [SL] (`Create`) [SW] (`Create`) [WCD]
4. **A backup must precede destruction of the old authority.** For SDK directory replacement, moving old→backup then prepared→live introduces a period with no live entry and at least two fallible steps. Reversing the first move is another operation that can fail. A backup-name collision is not permission to replace someone else's object; portability does not supply racing-writer no-clobber rename. [D1] [D2] [D4] [PR] [WM]
5. **Link backup is only entry backup, as selected by the user.** Renaming a top-level link preserves the link entry, not an immutable target snapshot; target drift/breakage does not invalidate verified entry ownership. Relative link text is interpreted from its containing directory; moving it into a different staging/backup parent may change its meaning. Direct-child sibling backup names preserve the parent for a top-level relative link; a nested backup directory does not. Compare/retain the entry's own target representation and identity/type evidence, not target contents, and account for final/restored parent semantics. No target-write/delete authority follows from this feature. [D4] [PH] [WH]
6. **Do not pre-delete the backup or live installation to make a rename work.** That creates additional failure windows and can discard the only surviving original. Backup existence alone is not proof of valid contents, correct transaction ownership or safe automatic restoration. [D1] [D2] [WREP]; inference from multi-step failure.

## 6. Permissions, open/locked files and concurrency

- **D/S:** `File.copy` has no general portable permission/ACL/xattr/mode/ownership-preservation contract. Linux copy creates destination with source `st_mode` passed to `openat`, filtered by umask for a new file; an already existing destination's mode is not reset merely by that creation-mode argument. macOS uses `COPYFILE_ALL`, which Apple defines as metadata (POSIX+ACL+xattr) plus data. Windows uses `CopyFileExW` through temp-copy/direct-copy paths. Microsoft documents preservation of extended attributes, alternate data streams, security resource attributes and file attributes; this is **not a complete portable DACL/owner/mode-fidelity specification**, and cannot be equated with POSIX modes. Directory creation is separate and is not a tree metadata copier. Exact ACLs, timestamps, ownership, streams, executable bits, sparse state and hard-link relationships are **not established as uniformly preserved**. [D1] [SL] (`Copy`) [SM] (`Copy`) [SW] (`Copy`) [PO] [AC] [WCP]
- **D/S:** `FileStat.mode` is readable, not a portable chmod/ACL API. Windows mode is synthesized from file attributes (`AttributesToStatMode`); it is not a complete security descriptor. Public APIs examined do not supply general chmod/chown/ACL preservation controls. It is not safe to infer “can delete/write” from a mode snapshot. [D3] [SW] (`Stat`, `AttributesToStatMode`) [WC] [WD]
- **D:** POSIX rename/unlink can remove a name while an open handle still accesses the old file; permissions on containing directories and special busy/read-only conditions still matter. Windows deletion can fail on read-only files, insufficient delete/delete-child rights, or incompatible open handles/mappings; sharing modes are established by existing opens. A successful preflight cannot promise subsequent rename/delete will succeed. [PR] [PU] [WD] [WC]
- **D/S:** `RandomAccessFile.lock` is byte-range locking, not a directory transaction. Linux/macOS use advisory process-level `fcntl` locks; any descriptor close by the process for that file can release locks, and several isolates in one process can acquire the “exclusive” lock. Windows uses handle-associated `LockFileEx`; unlock ranges must match, and writes via a different handle may fail. Windows docs also note byte-range locking does not block mapped-file access. [D1] (`RandomAccessFile.lock`) [SL] (`Lock`) [SM] (`Lock`) [SW] (`Lock`) [WL]
- **I:** Cooperating processes can coordinate through a stable lock object, with separate in-process serialization. Locking the replaceable `installations.json` file and renaming a new ledger over it does not transfer the lock to the replacement object. Other processes could lock/open the new entry instead. Likewise separate locks selected only by destination/profile labels do not serialize aliased physical roots. Neither POSIX advisory nor Windows byte-range locks protect a whole resource tree from arbitrary writers. [D1] [PR] [WL]

## 7. Flush, durability and crash consistency

| Level | What is established | What is not established |
| --- | --- | --- |
| Awaited stream operations | `IOSink.flush` drains to its underlying consumer; documentation explicitly says **not necessarily OS flush**. `close` is not a substitute for flushing pending sink data. [DS] | Stable storage or directory-entry durability. |
| `RandomAccessFile.flush`, `writeAsBytes/String(flush: true)` | API documents file/disk/filesystem flush. Source: Linux/macOS `fsync(fd)`; Windows `FlushFileBuffers(handle)`. [D1] [SF] [SM] [SW] | Atomic tree snapshot, joint ledger commit, directory-entry persistence, or unconditional power-loss recovery. |
| Linux file vs namespace | Linux `fsync` documentation requires an additional directory-fd `fsync` to ensure containing directory entry persistence. [PLF] | Dart has no public directory-open+fsync API. Flushing a temporary ledger alone does not durably publish its rename. |
| Apple storage ordering | Archived Apple docs distinguish ordinary `fsync` from `fcntl(F_FULLFSYNC)`, which also asks the drive to flush buffered data. SDK macOS uses `fsync`, not `F_FULLFSYNC`. [AF] [AFC] [SM] | No present-day APFS/device guarantee measured here; archived docs are not proof about every modern controller, volume or power-failure scenario. |
| Windows storage | `FlushFileBuffers` concerns a handle's buffered data; Microsoft documents caching and write-through/unbuffered considerations. SDK rename uses `MOVEFILE_WRITE_THROUGH`; its docs describe flushing copy/delete moves, not a multi-path transaction. [WF] [WM] [SW] [SDW] | No general durable ledger+directory atomicity follows from the flag. No portable directory durability control is exposed. |

**I:** Distinguish at least (a) API return/synchronous error handling, (b) process interruption with kernel/storage alive, and (c) OS crash/power loss. A design may be recoverable after (b) yet not claim durable ordering after (c). All flush failures must remain failures; successful flushes still depend on filesystem/device contracts. POSIX single-rename visibility is not a write-ahead-log protocol. [PR] [PLF] [AF] [WF]

## 8. Ledger transaction consequences and failure-state inventory

**I:** Installation content, link entry, backup, intent/recovery record and `installations.json` are distinct filesystem objects. Portable Dart provides no single commit spanning them. A recoverable design needs explicit transaction identity and before/after evidence, collision-safe staging, an ordering/recovery protocol, and conservative handling of ambiguous states. This is a logical consequence of §§4–7, **not** selection of a ledger schema or automatic rollback policy.

The table enumerates obligations/possible observations, not a proposed state machine:

| Interruption/failure point | Possible state | Constraint on a truthful guarantee |
| --- | --- | --- |
| Preparing staged candidate | Original live + old ledger; incomplete candidate | No early success/ownership claim. Distinguish transaction-owned scratch from an unrelated entry before cleanup. |
| Old live moved to backup | Live absent; old ledger and backup present | This is an expected gap in a two-rename design, not atomic replacement. Preserve evidence and backup. |
| New candidate published, ledger not committed | New live, old ledger, old backup | Baseline in old ledger cannot silently authorize new bytes or target. Need evidence tying new baseline to transaction; otherwise indeterminate. |
| Ledger update before content publication | New ledger, old/missing live | Reversing ordering moves the inconsistency; it does not solve joint commit. |
| Ledger temp write/rename fails | Old or new ledger may be present depending on completed steps | Avoid in-place JSON truncation; validate complete record and schema. A corrupt/missing ledger is not proof of unmanaged absence or deletion authority. |
| Restore fails (locked/collision/permission/IO) | Backup retained; live absent or occupied | Do not overwrite a newly arrived occupant or report “rolled back.” Report recoverable artifacts/indeterminate outcome. |
| Removal interrupted after partial deletion | Some files removed; original baseline no longer matches remainder | No all-or-nothing recursive-delete guarantee. A quarantine rename can separate visibility from later cleanup, but does not make bytes immutable or make the ledger jointly atomic. |
| Power loss after any step | Namespace/data ordering depends on fsync/storage support | Retained names or JSON intent alone do not prove durable recoverability; qualify unsupported storage and ordering explicitly. |

Additional constraints:

- **Copied-installation unchanged-only removal/replacement:** whole-installation manifest comparison must include membership (new/deleted entries), types and specified baseline attributes, not just `SKILL.md`, file size/mtime or “managed” ledger membership. Internal links are rejected. **Top-level linked installations use link-entry identity/type/target only, not a target-content manifest.** Verification of read bytes does not prove a future deletion sees those same bytes/entries. If quarantining before verification, a changed object may already have moved; if verifying first, it may change before moving. This trade-off needs a stated writer assumption, not hidden equivalence. [D2] [D3] [PU]; baseline scope from the issue/amendment context.
- **Ledger is data, not capability:** recorded relative paths/roots/backup paths must be revalidated and bounded before mutation. A ledger path cannot bypass direct-child eligibility or grant target deletion via an alias/link. Partial, unsupported or corrupt metadata cannot establish uniqueness or unchangedness. [D3] [D4]; issue constraints.
- **One physical authority:** per-scope ledgers and known consumer-profile uniqueness must account for aliased roots/Shared visibility. Independent profile records cannot independently remove the same object. A per-ledger lock does not automatically cover physical aliases or two scopes mapped onto one root. [D3] [D1] (locking); [destination amendment](https://github.com/louiss0/agent_resource/issues/5#issuecomment-6354750934).
- **Backups need a baseline too if later removed:** “temporary,” “backup” or “manager-created” is not evidence that a user has not edited it. Automatic cleanup must not silently relax the unchanged-only content-removal constraint. Recovery/cleanup of manager-only artifacts versus user resources needs explicit classification; research does not choose it.

## 9. Sharp remaining decisions / unproven guarantees

These questions belong to safety/CLI/design decisions, not to filesystem research. The live choices at the top remain fixed.

1. **Identity/verification contract within the chosen threat model:** Trusted local roots and no hostile-writer or guaranteed power-loss claims are settled. What SDK-observable versus native identity evidence is required, especially for a persisted link entry? What checks define observed drift and fail-closed verification? Do not imply strict compare-and-delete under arbitrary concurrent writers.
2. **Top-level link representation and identity:** The support boundary is now fixed: top-level skill-directory links only, no linked roots/internals; link-entry ownership only, permitting drifted/broken targets. What counts as the persisted entry identity and type: native file ID/reparse subtype or a deliberately weaker SDK-observable definition? Are existing junctions an accepted top-level representation? Unknown tags and hard-link aliases cannot be inferred safe from coarse SDK types. Missing Windows symlink privilege cannot become an undocumented junction/copy fallback.
3. **Link-backup mechanics, not target policy:** The entry-only baseline/backup boundary is settled. Remaining work is how to retain/verify identity, directory-link subtype and target representation across backup/restore, including relative targets and Windows decoded-vs-raw reparse data, without following or requiring current target content. Target restoration/deletion is not authorized.
4. **Storage envelope:** Which local filesystems, mount/filter conditions, permissions/ACL inheritance and OS/SDK versions are supported? Does “offline” exclude network-mounted paths and cloud placeholders whose filesystem drivers perform IO? No proof here that a syntactically local path prevents remote/filter activity.
5. **Recovery detail within the chosen scope:** Retained backups with explicit restore/cleanup are initial scope; guaranteed power-loss durability is excluded. Specify synchronous-error/process-interruption recovery boundaries, where evidence/backups remain, and when outcome is “failed but restored” or “indeterminate.” Restore/cleanup must refuse colliding/user-edited/unverifiable content. Pure `dart:io` still has no multi-object transaction.
6. **Metadata definition:** Which modes/ACLs/xattrs/streams/executable bits/link relationships count as baseline changes and which must be preserved? A general cross-platform exact-fidelity promise is unsupported. This must stay within the strict validator and inventory/hash/copy budgets, without executing resource code.
7. **Removal/replacement visibility:** Is a temporary absent-live gap acceptable? Does a quarantine move of an edited installation count as an impermissible change even if later restored? Replacing a nonempty directory atomically with retained backup is not a portable SDK primitive.
8. **Concurrency/authority and dry-run:** How are cooperating processes/isolates serialized across aliased physical destinations and scope ledgers, including a Shared installation with multiple consumers? How is dry-run kept entirely off write/recovery/lockfile-creation paths while reporting that its reads are not reservations? Unverifiable mutation gates refuse; no independent harness authority or automatic rebaseline is justified.

## Fail-closed facts to carry into the chosen scope

- A metadata lookup error reported as `notFound` is not proof of a free destination; incomplete/unreadable inventory or manifest is not proof of uniqueness/unchangedness. Unknown reparse forms, linked roots/internals, special-file substitutions and budget exhaustion cannot be silently accepted. [D2] [D3] [SW]
- A changed/unverifiable old **copy** cannot be replaced or removed. A changed/unverifiable **link entry** cannot be replaced or unlinked as the managed entry; a drifted/broken **target alone** is not entry drift and must not trigger target mutation or an unnecessary target-read gate. [D3] [D4]; current user policy.
- Permission, sharing, lock, rename, flush, backup and restore errors can occur after earlier successful checks. Preserve retained backup/evidence and report partial/indeterminate outcome rather than declaring rollback or cleanup success. No SDK overwrite fallback is justified by a rename failure. [WD] [WC] [WM] [D1] [D2]
- A backup at a different parent can change a relative top-level link's referent; restore/cleanup must operate on verified entry evidence, not recursively through the saved link. Hard-linked content is not independent snapshot evidence. [D4] [PH] [WH]
- Dry-run cannot create scratch/backup/lock/ledger artifacts or perform recovery as a side effect. Observations do not reserve later mutation rights. [D1] [D2] [D3]; current user policy.

**Research resolution:** facts reject blanket “atomic, race-free, durable cross-platform Dart filesystem transaction” claims. They support a qualified portable approach under the **already chosen** trusted-local-root/cooperative-operation assumptions, with explicit retained-backup recovery and observed-drift detection. Remaining native-identity/metadata gaps must be defined honestly or handled through a separately specified native layer. This note chooses no dependency, final transaction protocol or new product policy, and grants no target deletion authority.
