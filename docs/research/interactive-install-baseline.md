## What the walkthrough does and does not establish

The accessible ticket/map text supplies the sequence **discovery → selection → scope/method → preview → confirmation**, two official source links, and the warning that the supplied walkthrough is inspiration rather than evidence. It does **not** reproduce a complete step-by-step transcript or identify the transcript's revision. Therefore this is a verification of that sequence and a discrepancy checklist for common stronger readings, **not** an attestation that an unavailable historical transcript matched its contemporary release. None of the stronger readings in the table below is attributed to the user as a quotation. [Ticket][ticket], [map][map].

| Reading of the workflow | Pinned implementation / discrepancy |
| --- | --- |
| Every invocation asks every question | False: single skill, `-y`, explicit filters/targets, detected agent context, and single target-directory method selection skip questions. |
| All skills start selected in the interactive list | False in the main repository/local flow: no `initialSelected` passed; custom prompt defaults to empty selection. `-y` without a skill filter selects all; the separate skills.sh pack flow explicitly preselects its skills. |
| “Detected harnesses” is one mechanism | False: installed-directory heuristics and “running inside an AI agent” detection are different mechanisms. Neither proves runtime resource compatibility. |
| Symlink is always the default | False: default is copy for a single unique skills directory or all-Eve targets; symlink is offered for multi-directory targets. |
| Symlink means a live link to the user's input source | False for ordinary `add` symlink mode: it copies input to canonical storage, then links harness locations to that copy. Internal `link` mode is distinct. |
| Preview/confirmation gives ownership checks, backups or transactional replacement | Not established: preview checks path accessibility, while installer cleans/replaces entries. One aggregate confirmation is not per-installation ownership proof or an atomic plan. |
| Global tracking only / universal immutable lock semantics | Outdated as a generalization: separate project and global locks exist, and write failures can be ignored after successful filesystem work. |
| Non-TTY automatically means `--yes` | False: non-TTY alone prints a tip; required prompt cancellation exits 1. Agent-context detection, separately, enables `yes`. |
| Clix can reproduce the custom Vercel menu just by injecting `CliIO` | False: Clix raw menus read process stdin directly and lack the same cancellation/EOF contract. |

Sources for the first eight rows: [add.ts][v-add], [custom menu][v-prompt], [installer.ts][v-installer], [locks][v-local-lock]. Clix evidence follows below.

## Vercel: externally verified behavior

### Source parsing is not discovery, and neither is installation

1. `parseSource` classifies absolute/explicit-relative local paths, GitHub shorthand/URLs, GitLab, Azure Repos, generic Git/SSH, known hosted downloads, and arbitrary HTTP(S) well-known candidates. Shorthand can carry a subpath, `@skill` filter and fragment ref; subpaths containing `..` segments are rejected. Local classification does not prove existence. Aliases and configurable GitHub host behavior also exist. This is not a promise to recursively search arbitrary websites. [source-parser.ts][v-parser]
2. `runAdd` validates local path existence, attempts well-known discovery for that source category, otherwise resolves/fetches and discovers skills. `resolveSkills` uses the local tree, downloaded file/archive, eligible GitHub blob snapshot (except full-depth), or clone fallback. Special Notion preparation and well-known flows have their own handling; main-flow defaults should not be generalized to all providers. `--list` reports candidates and returns without installation. [add.ts, resolveSkills and runAdd][v-add]
3. `discoverSkills` recognizes `SKILL.md`, requiring truthy **string** `name` and `description` frontmatter. Internal skills are hidden unless enabled by environment or explicit named request; bulk `*` is not that explicit request. A valid root skill returns early unless `fullDepth`. Priority locations include root, `skills`, curated/experimental/system and harness-specific skill directories, plus manifest-declared paths. Known containers descend three levels; root and manifest paths preserve depth-one scanning. Recursive fallback runs if no skills found or full-depth, with depth limit 5 and ignored build/cache directories. This is bounded discovery, not exhaustive whole-repository indexing. [skills.ts][v-skills], [constants.ts][v-constants]
4. Names normally deduplicate first-found; `includeDuplicateNames` can preserve duplicates for other callers. Source project-lock names suppress already-installed skills under recognized harness skill directories, rather than republishing dependencies as authored source skills. Parse/discovery failures can warn/skip; absence from the result is not proof a directory contains no resource. [skills.ts][v-skills]

### Selection, harness detection, scope and method

- Main-flow skill choices: explicit `--skill '*'` selects all; explicit names use case-insensitive exact name matching; no matches fails; one skill or `yes` auto-selects. Otherwise the custom searchable/groupable multiselect requires a nonempty result, offers Select All, and begins with no selected skills. Sorting/grouping affects presentation, not additional discovery. [add.ts, lines 1956–2040][v-add], [skills.ts][v-skills], [custom menu][v-prompt]
- Installed harness detection executes each `agents.ts` configuration's `detectInstalled` callback. Examples: Claude home directory existence; Codex configured home or `/etc/codex`. This is heuristic presence, **not** executable version verification or proof of discovery/activation. `getUniversalAgents` is configuration-based (`skillsDir === '.agents/skills'`, excluding explicitly hidden entries), not a runtime capability probe. [agents.ts][v-agents]
- Separate execution-context detection delegates to `@vercel/detect-agent`, caches the result, maps names, and refines Cursor to require stronger signals than `CURSOR_TRACE_ID` alone (`CURSOR_AGENT` or extension-host `agent-exec`). Main `runAdd` sets `yes` when an agent context is detected, and supplies mapped harness plus universal targets unless explicit targets were given. Exact upstream detector environment precedence was **not** independently audited; only this pinned wrapper and call-site behavior are established. [detect-agent.ts][v-detect], [add.ts][v-add]
- Explicit `--agent` bypasses detection selection; invalid names fail, `'*'` means all configured harnesses. Without explicit targets: Eve gets a special preferred-target confirmation (automatically accepted under `yes`); zero detected harnesses prompts over all non-Eve choices, or selects all with `yes`; one detected harness or `yes` selects detected plus universal; multiple detections otherwise use the interactive selector. [add.ts, lines 2060–2162][v-add]
- The **zero-detection** `promptForAgents` helper starts from valid saved history, else Claude Code/OpenCode/Codex/Grok defaults. The **multiple-detection** selector instead locks universal targets and starts other targets from saved non-universal history, else empty. These are not the same initial-selection policy. Selection history is persisted before final installation confirmation; cancelling later can still leave that preference effect. Eve can additionally select skill destinations in its existing subagent directories; that is **not** installation of agent definitions. [add.ts, lines 479–590 and 2160–2205][v-add]
- Scope defaults project (`global ?? false`). With no explicit scope, no `yes`, and at least one target supporting global installation, scope menu offers Project first, then Global. Method is copy for one unique target skills directory or all-Eve; otherwise symlink. `--copy` forces copy; without `yes`, a multi-directory symlink default prompts with Symlink first (“Recommended”) and Copy second. Thus the inspirational ordering exists, but not every step is mandatory. [add.ts, lines 2205–2266][v-add]

### Preview, replacement, storage, tracking

- Before effects, project scope reads its lock and rejects unusable lock state. Preview lists canonical paths, targets/method and “overwrites” from `isSkillInstalled`. That helper essentially tests `access()` at a sanitized target path, not resource validity, tracked ownership, a content diff, or a snapshot reserved against changes. The summary is followed by optional advisory audit information and one “Proceed with installation?” confirmation unless `yes`. [add.ts, lines 2238–2403][v-add], [installer.ts, lines 632–663][v-installer]
- Copy mode cleans destination and copies directly into each harness's skills directory. Symlink mode cleans/copies into project `.agents/skills/<sanitized-name>` or user `~/.agents/skills/<name>`, then links other harness entries to it. Universal targets use canonical directly; Eve has special canonical placement. Guards skip source/destination overlaps; missing project harness roots may skip link creation unless explicitly requested (with configured exceptions such as Claude). Link creation resolves parent links, uses Windows junctions, and falls back to copying if link creation fails, reporting the fallback. This is evidence of an implementation's storage arrangement, **not adoption of Agent Resource's “managed installation” or “linked installation” semantics**. [installer.ts, lines 133–195, 229–465][v-installer]
- `cleanAndCreateDirectory` removes existing entries recursively before recreating. Copy skips special metadata files and confines dereferenced symlink targets to the skill root. Those guards do not amount to a recovery-backup protocol or all-target rollback; individual results can succeed/fail separately. Do not reinterpret aggregate confirmation as safe authorization to delete arbitrary unmanaged resources in Agent Resource. [installer.ts, lines 191–205 and 526–628][v-installer], [add.ts, installToTargets][v-add]
- Global tracking: version-3 `.skill-lock.json`, normally `~/.agents/.skill-lock.json`, or `$XDG_STATE_HOME/skills/.skill-lock.json`; entries keyed by skill name store source/type/URL, optional ref/path, folder hash, timestamps and optional plugin/well-known metadata. Also stores last-selected harnesses/dismissals. Project tracking: version-1 `skills-lock.json`, keyed by skill name, source/type, optional source URL/ref/path, computed content hash, optional package provenance/Eve placement. It is not a per-target ownership ledger. [skill-lock.ts][v-global-lock], [local-lock.ts][v-local-lock]
- Main-flow writes are conditional on successful skills/scope/source; direct downloads are excluded from project tracking; missing hashes can skip project entries. Write failures inside per-skill recording are swallowed, so filesystem installation and tracking are **not atomic**. Global and project lock invalid/old-format handling differ. No general “all sources always tracked” claim is supported. [add.ts, lines 2449–2550][v-add], [lock readers][v-global-lock], [project reader][v-local-lock]

### Cancellation and automation

- Custom menu handles Escape / Ctrl-C as cancellation, closes/restores raw mode, and treats readline close/EOF or already-ended/destroyed stdin as cancellation. Main pre-install cancellation cleans temp source data, emits cancellation and exits **0 on TTY**, **1 on non-TTY** with explicit `--agent … -y` guidance. Declining final confirmation uses that same path. This is pre-install cancellation, not verified rollback or Ctrl-C cleanup after effects start. [custom menu, lines 568–698][v-prompt], [add.ts, exitInstallationCancelled][v-add]
- Non-TTY alone does not set `yes`; agent-context detection does. `--all` implies skill `*`, agent `*`, and `yes`; `yes` skips confirmation and scope/method questions and auto-selects skills without a filter. `--json` requires `yes`/`all` (including detection-induced yes), rejects list, and is explicitly unsupported for well-known skill sources at this revision. CI-specific frozen-lock behavior in the separate restore command must not be mistaken for `add`'s prompt policy. [add.ts][v-add], [install.ts][v-install]

## Resolved Mamba 1.0.0 / Clix 1.2.0

Source paths in this section refer to the byte-verified versioned archives above, **not** whatever happens to be on upstream GitHub `main`. [Versioned Clix API][c-api], [versioned Mamba API][m-api].

| Capability | Actual resolved implementation and limitation |
| --- | --- |
| Multi-selection | Clix `MultiSelect` (`lib/src/prompt/multi_select_prompt.dart`) accepts `prompt`, string `options`, zero-based `defaults` (empty by default), `help`; returns `Future<List<int>>`. Arrows move, Space toggles, Enter returns indices in option order. Empty selection is accepted; no required/minimum, locked universal section, grouped searchable multi-selection, or domain identifier mapping is supplied. |
| Confirmation | `Confirm` (`confirm_prompt.dart`) returns bool; trims/lowercases line input; only `y`/`yes` accepts. Empty answer uses nullable `defaultValue`, else false; **invalid text is false, not retry**. Despite documentation saying a null default “requires explicit choice,” implementation does not enforce a nonempty response. |
| Line input | `Input` (`input_prompt.dart`) trims input, can use default/validator, may retry. `ConsoleIO.readLine()` (`core/io/console_io.dart`) is synchronous `stdin.readLineSync() ?? ''`: ordinary EOF and blank are indistinguishable if read succeeds; OS errors can still throw. Repeated required validation at EOF can repeatedly retry. |
| Injectable I/O | `Prompt.interact([CliIO?, CliTheme?])` supplies `run`; `CliIO` exposes write/writeln/readLine/isTTY, not nullable EOF or byte input. Text and confirm use this boundary. `PromptGlobals` supplies mutable defaults, but is not barrel-exported. The shipped `MockIO` is also **not** exported from `clix.dart`; a local probe needed its `src/` import. Application-owned `CliIO` implementations avoid relying on that internal import. |
| Raw input bypass | `Select`, `MultiSelect`, `Password` and Search's result menu use process `stdin`, despite injected `CliIO`. They synchronously change echo/line mode and read bytes; `.interact()` returning Future does not make these reads nonblocking or injectable. |
| Cancel / EOF | MultiSelect and Select have **no explicit Escape/Ctrl-C/EOF result branch**. MultiSelect treats Escape as a three-byte arrow prefix; bare Escape can wait for two more reads. Neither handles `readByteSync() == -1` as termination, so an environment permitting raw-mode reads at EOF can loop/render rather than cancel. Terminal setup itself can fail for a pipe; setup occurs before their `try/finally`; finally resets modes to true, not saved previous values. Ctrl-C OS/process behavior is host-dependent, not a library-level typed cancellation guarantee. Search's result menu instead uses `r` to search again and `q` to quit, with quit becoming `Exception('Search cancelled')`; it is not a shared contract. |
| Terminal detection | `ConsoleIO.isTTY` reports `stdin.hasTerminal`; this does not certify stdout styling, raw-key support, or a usable handle. Raw menu code does not gate itself with `io.isTTY`. `MockIO.isTTY` is false, but confirm still runs with it. |
| Mamba adapter | `lib/components.dart` defines `ClixInput` alias and line-based `ClixSelector`: numbered single selection/search over strings, empty choices/blank yields null; **not a multiselect**. `ClixDirectoryPicker` uses that selector. Mamba reexports Clix (`lib/mamba.dart`) while preserving Mamba's typed argv `Input`. Generated render wrappers use default interaction I/O rather than accepting per-render `CliIO`. |
| Executor testing | Mamba `Executor.fake(standardInput: ...)` (`lib/executor.dart`) only replaces framework stdin delivery to pre-hooks, result delivery and process status/streams. It neither answers prompts nor suppresses command-owned prompt/filesystem/network effects. `create()` buffers pipe/file input to EOF at selected pre-hook boundary; that input is not an interactive answer channel. Automatic help terminal capability injection controls help presentation, not prompt eligibility. |
| Clix test helper | `lib/src/testing/cli_test_runner.dart` uses `Process.run` plus Future timeout/captured output; no input-script/PTY driver is exposed there. A timeout does not provide raw-key/cancellation fidelity. Line prompt unit tests and executor tests do not establish Windows terminal interaction behavior. |

All table implementation claims: [Clix 1.2.0 official source archive][c-archive] and [Mamba 1.0.0 official source archive][m-archive]; inspect the named paths rather than relying on some stale class names/examples in Clix barrel documentation. Mamba's repository-local [prompt component reference](../../.agents/skills/mamba-framework/references/prompt-components.md) independently cautions about raw-stdin bypass, fake-executor boundaries, and EOF; package source was checked rather than treating that reference as sufficient evidence.

### Bounded runtime observations (Windows / Dart 3.13.2)

An uncommitted scratch script outside the original checkout ran with `dart --packages=C:/Users/bvlou/projects/agent_resource/.dart_tool/package_config.json <scratch.dart>`:

- Injected Clix `MockIO`: `Confirm(defaultValue: false)` returned true for `yes` and ` Y `, false for `n`, `invalid` and empty input. Mock reports non-TTY, yet confirm still executes.
- Mamba selector with `['alpha', 'beta']`, responses `['beta', '1']`, returned `beta`; exhausted mock input returned null for a nonempty selector.
- Python `subprocess.run([...dart..., 'eof'], input='', capture_output=True, timeout=20)` supplied a real closed pipe. `ConsoleIO.isTTY == false`, but `Confirm(defaultValue: true)` **returned true**, process exit 0, and emitted ANSI output. EOF is therefore capable of accepting a default-yes confirmation unless the caller prevents or distinguishes it.
- A separate Git-Bash-style `< /dev/null` invocation failed with `StdinException: Error getting terminal line mode`, Windows invalid handle errno 6, rather than returning a blank. That is an observed launch/handle limitation, **not** evidence that all redirected input fails. The Python pipe observation above succeeded.

No raw-menu probe was run against an uncontrolled live console or intentionally unbounded EOF loop. Static risks are labelled as such; Ctrl-C delivery, console-mode restoration, Windows arrow-key encoding and actual PTY EOF/cancellation remain acceptance-test needs, not runtime-certified features. No upstream tests or Agent Resource application tests were run for this documentation-only research.

## Inputs for later decisions, not decisions here

The sourced workflow supports an explicit discovery/choice/review boundary, but does not settle Agent Resource's default selections, prompt eligibility, source coverage, harness compatibility, overwrite/adoption authority, installation identity, partial-failure semantics, cancellation statuses or migration. Those remain map/HITL work. In particular:

- Native **agent definitions** require resource-specific discovery/compatibility evidence; Vercel Skills' target “agents” are mostly consuming **harnesses**, not proof of portable agent-definition support.
- Choosing Clix raw MultiSelect requires an application-owned answer/terminal/cancellation test boundary beyond `Executor.fake()` and injected `CliIO`; choosing line-based interaction would be an adaptation, not identical raw-key Vercel UX.
- A preview is an observation, not a filesystem reservation; later safety/ownership work must decide revalidation and replacement rules. Vercel's canonical copy and name-keyed lock are comparison evidence, not an approved Agent Resource persistence model.

These are constraints/questions exposed by evidence, not policy resolutions. [Map Notes][map], [Agent Resource vocabulary](../../GLOSSARY.md).
