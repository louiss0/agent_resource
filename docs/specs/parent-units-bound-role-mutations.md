## Problem Statement

An Agent definition cannot express every prerequisite of a working native Agent. Permissions, sandbox settings, provider/model defaults, MCP registration, and Codex role registration may belong to shared parent configuration rather than the definition itself. Developers need deliberate control over those changes without allowing an Agent operation to silently reconfigure a parent, claim an entire account/configuration document, expose credentials, or erase unrelated settings during recovery.

This is roadmap **checkpoint 6: parent setting units and bound-role mutations**. Existing read-only inspection is not write authority, and the current uncommitted regular-file implementation is not a verified selected-unit transaction engine.

## Solution

Provide explicit inspect, plan, and apply workflows for supported native Claude/Codex parent configuration changes, with exact source/layer selection, source-preserving patches, selected-unit ownership, redacted impacts, source-bound approval, private recovery, and stopped-client acknowledgement. Extend request-based Codex bound-role management while keeping registration ownership separate from definition ownership. Common Pi parent settings remain report-only.

The user reviews what will change, where it will change, what known associations may be affected, and what remains conditional or unverified. A preview creates no management artifacts. Apply reconstructs that exact plan and refuses stale or unsafe state. Normal restore patches approved prior units into the current document rather than overwriting it from an old whole-file snapshot.

28. As a user, I want private staging and recovery protection established before sensitive bytes are written, so that random filenames do not stand in for confidentiality.
29. As a Codex user, I want role selection through a bounded request identifying declaring config and role key, so that a standalone path is never reinterpreted as a binding.
30. As a Codex user, I want to select registration ownership, definition ownership, or both explicitly, so that a reference does not silently acquire a file.
31. As a Codex user, I want referenced role paths resolved from the declaring configuration, so that request location and CLI cwd do not change native meaning.
32. As a Codex user, I want eligible referenced definitions outside ordinary Agent directories explicitly adoptable within the approved boundary, so that real native roles can be managed without granting arbitrary write roots.
33. As a Codex user, I want strict name uniqueness including known builtins and all required visible candidates, so that role management does not introduce hidden shadowing.
34. As a Codex user, I want new bound-role publication to use an explicit reviewed creation request, so that standalone install never silently registers a role.
35. As a user, I want managed role replacement/removal to use recorded IDs and selected-unit baselines, so that destructive lookup cannot drift to another role or scope.
36. As a user, I want shared definitions and other registration references preserved unless separately selected, so that removing one binding does not cascade into unrelated users.
37. As a user, I want private retained backups of selected prior units or absence, so that routine recovery does not become whole-account version history.

## Implementation Decisions

### Explicit commands and operation requests

- Add concrete agent config inspect, agent config plan, and agent config apply commands under a new config group within the existing agent group. Each leaf owns its retained typed request/context/approval/output declarations. Keep shared planning/patching/transaction work in focused domain services; no generic resource/operation command factory, universal Agent model, arbitrary-key editor, or replacement argv parser.
- Extend concrete Agent adopt, replace, and remove commands with mutually exclusive request-based bound-role selection. Requests identify exact declaring configuration, role key, explicit native context, applicable managed IDs, and registration/definition/both ownership intent. No role/config/own selector-flag substitute and no destructive native-name search. Preserve direct stored-ID file operations.
- Implement only the bound-role creation branch needed here through a concrete Agent create command: an explicit request selects a supplied native definition source, eligible destination, exact registration, and ownership decisions. Validate the proposed definition in its candidate binding context. It is a reviewed publication operation, not a general native builder or transitive composition feature; do not register unimplemented rich command paths. Standalone install never implicitly registers. Complete general composition remains checkpoint 7.
- Use matching Mamba generators for new commands/groups and other supported declarations, wire every generated command into the actual production tree, and replace starter tests with behavior coverage. Only the production entry point uses Executor.create; command tests use Executor.fake.
- Requests are strict versioned operation data, not a new cross-harness configuration language. Enforce operation/command agreement, explicit native source/target or managed identity, exact supported payloads, duplicate-key rejection, unknown-envelope-field rejection, context agreement, and no unsupported versions/selectors/new credential literals. Preserve the existing read-only bound-role inspection request contract; add separate operation-specific validators rather than silently reinterpreting old inspection requests as write requests.
- Parent requests select source/scope/layer explicitly and never inherit Agent project default to choose a parent file. Operation/request-level relative paths resolve against selected cwd; native references keep their documented bases. Read-root authorization never grants ownership or write eligibility. Typed input suffixes are completion hints, not content/schema validation.

### Native scope and selected-unit authority

- Support evidenced Claude/Codex native permissions/sandbox, model/provider/default settings, MCP registration, and Codex role registration using native-specific typed operations. Managed/system/session-enforced sources are inspect-only. Common Pi parent settings remain report-only. No global fallback, trust escalation, account login, native activation, dependency installation, or helper execution.
- Refuse ineffective Codex project-provider routing and offer an eligible user-source alternative only as a new explicit plan. Legacy and beta permission families are explicit mutually exclusive plans; configuration-profile files and permission profiles are distinct. Do not claim domain enforcement without documented proxy conditions or project support for ignored keys.
- Parent ownership is keyed by exact physical source/scope/layer and selected native semantic unit: scalar/map entry, supported membership in an unordered rule list, or the whole value of a genuinely ordered array. No unstable index ownership or automatic acquisition of parent containers. Existing units require explicit adoption; whole-entry deletion requires ownership/review of that entire entry. Detect equal and ancestor/descendant overlap and semantic membership conflicts. Serialize all cooperating edits to one physical document even for disjoint owned units.
- A Codex binding's identity is declaring configuration plus role key; a definition's identity is its recorded physical location. Registration and file ownership remain separate, with one authority per physical artifact or selected unit. Eligible explicitly referenced role files can be adopted inside the approved project/configuration boundary; outside files stay reference-only without new authority. Reserved parent/auth/state/management files cannot be acquired wholesale as definitions.
- Use existing native binding/inspection semantics for metadata fallback, relative references, target-form validation, and uniqueness. Include known builtins and all required visible scopes without inventing runtime winners. Exclude only the selected verified occurrence, not another conflicting declaration. Linked Agent definitions remain unsupported. Removing a registration never implicitly deletes its definition, dependencies, shared settings, other roles, memory, or transcripts.

### Source-preserving plans and apply

- Introduce a focused native parent-plan/patch service with immutable outcomes for readiness, coverage, provenance, selected before/after intent, ownership/adoption, conflicts, and redacted known impacts. Separate configured changes, source-qualified interpretation, shadowed/conditional authority, and unverified runtime activation. Unknown unselected native members are preserved; unresolved requested semantics block writes.
- Make bounded span-based edits against the original document and preserve all bytes outside approved edit spans, including TOML comments, newline convention, unrelated ordering/whitespace, and unknown values. Claude strict-JSON sources do not accept comments/JSONC. Preserve supported encoding/BOM and terminal-newline behavior explicitly; refuse unsupported encodings rather than lossy rewriting. Keep UTF-16 parser offsets distinct from UTF-8 byte budgets so Unicode cannot shift edits. Reparse and validate the whole proposed candidate plus selected native semantics. Duplicate/ambiguous syntax or unsupported precise edits refuse; never fall back to generic map reserialization or regex-only configuration rewriting. Coalesce nonconflicting patches to one document into one candidate.
- Long-lived baselines cover selected units and distinguish absent from present values. Separately capture full-document fingerprints for plan freshness. Any document drift invalidates apply even if owned units still match. No automatic rebase, retry, merge, force, or baseline reset. Stable plan IDs bind request, operation, profile, context, source/target observations, proposed changes, ownership and field/impact decisions; exclude random IDs and volatile timestamps.
- Inspection/planning creates no stored plan, locks, logs, journals, staging, ledger, or backups. Noninteractive parent apply requires the matching reconstructed plan ID, ordinary approval, and a separate apply-time clients-stopped acknowledgement. Request-based role creation/mutations plan by default and require explicit apply, plan ID, and approval; any parent-writing branch additionally requires that acknowledgement. Apply and dry-run conflict. Explicit interactive apply may review/confirm a fresh plan in the same invocation, with the same validation and specific decisions. JSON/interactivity conflict; prompts never occur by default.
- Subsequent operator-invoked parent-writing restore/recovery requires a fresh action plan identity and apply-time clients-stopped acknowledgement, not merely the original apply approval. Narrow in-transaction compensation during the same already-approved apply invocation is part of that exact transaction: the reviewed plan must disclose its guarded restoration scope, and the current invocation's approval/acknowledgement covers only restoring its own provable prestate. It needs no second prompt/plan exchange, must not cross into separately completed operations, and must stop with recovery-required evidence if current-path/source guards no longer hold. Generic approval is not ownership adoption, intentional impact consent, field decisions, uncertainty bypass, or quiescence acknowledgement. Do not enumerate processes as proof or stop native clients automatically.
- Allow valid deliberate downstream restriction/removal only with specific approval identifying known affected associations. Do not allow malformed native controls, unresolved patch semantics, higher-policy bypass, or required dangling references inside the parent document. Show exposed lower-layer/default effects. Keep bounded impact coverage explicit; do not promise all Agents remain valid or every live dependency was inspected.

### Sensitive data, storage, and transactions

- New credential literals are not supported inputs or generated settings. Accept only evidenced native credential references or separately configured authentication; never resolve values, inspect auth stores, execute helpers, or assume arbitrary JSON/TOML strings interpolate. Preserve unrelated existing secrets without displaying them. Field-aware redaction is not omniscient detection of secrets hidden in arbitrary prose/commands.
- Claude mixed account/trust-state writes require established location and project-entry identity for the exact native variant. Unresolved relocated variants remain inspect-only; no guessed filename/key normalization, whole-object takeover, native CLI fallback, or auth migration. Project and local MCP sources remain distinct from ordinary settings sources.
- Verify private same-filesystem staging/recovery protection before sensitive bytes are written. Necessary full-document candidates/originals are private transaction artifacts, not ordinary ownership metadata or retained account history. Refuse if required native confidentiality cannot be established. Ordinary records contain identities, fingerprints, selected-unit evidence, and controlled diagnostics, not complete parent bodies or secrets.
- Retain verified private selected prior unit states or absence markers for parent recovery; retain independent verified file bytes for owned definition replacement/removal. Quarantine/originals are not independent immutable backups. Normal parent restore freshly parses the current document, verifies current owned-unit state, rechecks native validity, approval, full-document freshness, and quiescence, then restores only approved units while preserving unrelated newer state.
- Prepare bounded staged native and management updates before publication. Persist protected intent, coordinate physical sources and inventory, apply the exact approved multi-file plan, verify results, and tie record commits to observed state. One role-file plus explicitly selected registration may be one recoverable operation. Separate completed prerequisite operations are never silently compensated if later work fails.
- Failed restoration may use an original full document only against provable exact current-state/path guards. Never overwrite unrelated later updates or a new occupant. If safe selective restoration or completion cannot be proved, retain protected evidence and report recovery required. Recovery is evidence-backed and idempotent/refuses changed evidence; cleanup cannot erase the only recoverable prior state. Restoring settings cannot undo hooks, remote effects, credentials, or existing sessions.
- Extend versioned records with typed parent-unit/registration artifacts and explicit compatibility rules. Preserve supported existing file/copy/link evidence; unknown kinds/versions refuse without ownership reset. Agent backup/recover handles typed Agent and parent artifacts in the existing scope-safe branches, not duplicate configuration backup/recover commands.
- Keep status meanings: 0 completed report/plan or operation; 1 invocation/request/general failure; 2 blocking correctness; 3 incomplete required analysis; 4 safety/ownership/approval refusal; 5 failed but restored; 6 recovery required/committed required cleanup pending; 7 cancellation. Complete read-only not-ready plans may succeed and explicitly report no writes; unreadable required coverage or exhausted budgets cannot be relabelled completed plans. Handled failure emits stderr and no success JSON/stdout.

### Bounds

- Parent source documents: 8 MiB each, parse depth 64, 100,000 nodes each; at most 16 target files and 32 MiB aggregate source per plan. Proposed/staged candidates: 8 MiB each and 32 MiB aggregate; parse/validate candidates within the same structural limits before publication.
- Requests/management documents: 8 MiB each, parse depth 32, 100,000 nodes each; 64 MiB aggregate management metadata processed per transaction. Keep native definition limits separately binding. Required graph work retains depth 32, 1,000 nodes, 5,000 edges, and 16 MiB inspected source. Inventory retains 64 ancestors/depth 16/20,000 entries/2,000 directories/64 MiB metadata.
- Enforce limits during reading, parsing, planning, editing, serialization, and staging, not after unbounded allocation or expansion. Hitting any independently applicable budget blocks required application work; no unlimited override or partial-success truncation.

### Library recommendations

- **Reuse existing libraries:** Mamba for individually declared commands, package:toml for supported semantic parsing/validation of Codex documents, dart:convert for bounded JSON value encoding/decoding after syntax/duplicate checks, package:crypto for source/plan fingerprints, and package:path for lexical paths. None establishes ownership, bounded processing, comment preservation, or native policy by itself.
- **Recommended TOML approach:** keep package:toml 0.18.0 for semantic validation, not lossless printing: its parser discards comments/blank trivia and its printer reformats. Prototype source-range capture around its public grammar using the already-transitive package:petitparser 7.1.0 Token API (buffer/start/stop), then validate selected-unit edits and untouched slices. Whole-expression tokens alone do not locate every nested unit; parser-time limits and quoted/dotted keys, inline tables, arrays of tables, and multiline strings need explicit proof. Declare petitparser directly if imported. Do not introduce a second universal TOML grammar or fall back to reserialization when a precise edit is unsupported.
- **Recommended JSON approach:** extend the existing duplicate-key-aware bounded reader concepts with member/value/container source ranges and exact separator handling; do not decode/edit/encode the whole parent map. Reject duplicate decoded keys, including escaped-equivalent spellings, during parsing. Optional already-transitive helpers are package:source_span 1.10.2 and package:string_scanner 1.4.1; they supply ranges/scanning, not native semantics or automatic budgets. Use consistent UTF-16 source offsets and enforce UTF-8 byte caps separately. Declare direct dependencies if imported, and do not add them merely to replace an adequate existing scanner.
- **Rejected recommendations:** the verified toml_edit package is Rust, not a Dart drop-in (the Pub lookup returned no package); json_ast 1.0.6 declares a Dart SDK upper bound below 3.0 and is incompatible with this project; yaml_edit does not edit these native JSON/TOML families. No dependency override, cross-language helper build, or speculative new editor is selected.
- **Privacy/native adapter:** package:win32 6.4.0 with package:ffi 2.2.0 is a conditional Windows recommendation, not a complete ACL/reparse/identity solution: the examined archive lacks several required descriptor and extended-ID bindings. Supplement only measured gaps with focused FFI or a small native shim; use OS-specific POSIX bindings only where existing primitives cannot establish required behavior. Restrictive native creation and actual ACL/ownership verification are preferable to create-then-chmod/icacls text checks; never write sensitive bytes before protection is established. Reuse proven native guards from the earlier checkpoint, but do not infer private storage or handle safety from a package's existence.
- Do not add a secrets manager, runtime configuration watcher, general dependency-injection framework, shell/harness wrapper, or new CLI parser. No dependency is installed by this spec. Validate compatible versions, exact parser/token APIs, license and maintenance, preservation/security behavior, and committed-lockfile native tests before adoption; missing capability blocks an implementation claim rather than weakening requirements.

## Testing Decisions

- The user confirmed the existing seams: production command-tree acceptance through Executor.fake with real isolated filesystem fixtures, focused public service tests for deterministic exceptional IO/forbidden-read assertions, and actual built-production executable smoke on native Windows/macOS/Linux. Prefer these boundaries over private helpers, mock-everything tests, or another framework.
- Prior art includes concrete Agent inspect/validate tests, strict bound-role request/binding cases, isolated Skill/Agent public-operation tests with injected publication/journal/rollback failures, and sanitized process fixtures. Reuse native relative-reference and fallback facts without treating read-only observations as management authority.
- Test each supported native source/scope/layer and operation family, Codex legacy/beta separation, project-provider refusal, managed/system/session inspect-only handling, Pi report-only behavior, known authority/shadowing and lower-layer effects, and specific intentional-impact decisions. No live client, account, credential, MCP, or network requirement.
- Use independently authored native fixtures: strict JSON with escaped/duplicate-key cases, and TOML with comments, quoted/dotted keys, inline tables, arrays of tables, and multiline strings; both include unknown members, ordering, Unicode/non-BMP text, line-ending/terminal-newline cases, and synthetic unrelated secrets/account state. Assert strict-JSON comment rejection rather than silently enabling JSONC. Assert exact bytes outside approved edit spans, correct selected native values, unchanged other roles/resources, and redaction across plans, results, diagnostics, ownership records, and ordinary logs. Prove privacy is established before sensitive writes; random naming is not the assertion.
- Test explicit unit adoption; absent/present baselines; scalar/map/unordered-membership/ordered-array semantics; disjoint and overlapping unit ownership; same-document candidate coalescing; full-file stale-plan rejection after unrelated edits; no silent rebaseline; normal restore preserving unrelated later state; and unsafe stale whole-account rollback refusal.
- Exercise request-only Codex creation/adoption/replacement/removal, metadata-only bindings where native form permits, explicit registration/file/both ownership, outside-standard-directory eligible references, shared definitions, strict per-target/builtin conflicts, wrong-scope IDs, reserved/outside-boundary paths, and references resolved from declaring configuration. Assert no implicit registration, file acquisition, dependent deletion, or policy bypass.
- Through actual commands, test exact retained inputs and exclusive source/request layouts, schema/version/operation/unknown/duplicate rejection, context agreement, stable plan IDs, changed-source/request/context/profile/decision invalidation, default read-only role requests, explicit apply approval, required parent quiescence acknowledgement, cancellation, help/parser no-effects, and JSON/interactivity conflicts. Preserve existing inspection-request compatibility and direct file command behavior.
- Test each source/candidate/management/graph/inventory limit at the boundary and one-over, including incremental reads/parses/generated output; controlled IO assertions prove forbidden reads and helper execution did not happen. No expected result is recomputed using the implementation's own patch/hash logic as the sole oracle.
- Inject faults/interruption at every prepare/backup/intent/publication/verification/record/restore/cleanup boundary, including between files and during recovery. Reconstruct from persisted evidence; assert live native values/bytes, selected ownership, protected backups/journals, and unaffected sentinels. Cover new occupants, unrelated mixed-state updates, corrupt evidence, ACL failure, locked entries, flush failure, committed cleanup pending, repeated recovery, and separately completed prerequisites that remain committed.
- Every native OS job requires positive narrow parent edits, native Codex bound-role workflows, synthetic established Claude mixed-state preservation, private retained backups, unit-scoped normal restore, applicable permission families, and built-production executable positive/refusal stdout/stderr/status smoke. Source-script-only smoke, mocks, WSL/emulation, or green skips do not qualify native behavior. Rare real 5/6 outcomes may run on capable native jobs; retain real 0–7 evidence across the release.
- Completion requires traceability for every user-visible rule/safety transition, selected release SDK and committed lockfile, formatting/analysis/focused/full suites, and revision/artifact/dependency/OS/filesystem/capability/job evidence. Missing native privacy/positive/status evidence or unresolved safety/flakiness blocks release claims. Tests establish application behavior, not runtime harness activation or enforcement.

## Out of Scope

General native Agent building/composition beyond the minimal bound-role publication branch; all-six conversion; Pi parent writes; managed/system/session-policy mutation; arbitrary configuration editing; inferred shell/prose dependencies; automatic client shutdown; process-based proof of quiescence; resource/helper/harness execution; live enforcement, login, connectivity, or account probes; credential import/migration; whole-account retained history or normal full-document restore; automatic dependent rewrites/deletion; hidden scope fallback; remote origins; hostile-writer resistance, joint multi-file atomicity, guaranteed power-loss durability, or reversal of external effects.
